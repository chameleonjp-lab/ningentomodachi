# ニンゲントモダチ 全体実装計画書

計画版1 / 2026-10-22 JST / 状態：計画のみ。実装・PR作成・公開は未実施。

## 1. 基準と完成の定義

基準資料は「ゲーム設計書 レビュー版6」。SHA-256：8baa701cb13546ae7e7dddb1c4296f97f0758443cfa90d9b4f777d76b4f5d217。今回の依頼は、この資料を使う全体・個別計画と指揮担当運用指示書の作成であり、実装開始の依頼とは区別する。

完成品は、スマートフォンでタイトルから開始し、同じパリ風の通りを移動、横視点の1対1を4回進め、クリアまたは敗北で採点し、再挑戦できるブラウザゲーム。素材表示だけ、検査用の箱だけ、計算だけの完成を全体完成としない。

- 白・通常敵はHP500。敵は青・緑・黄・黒の計4体、1体ずつ戦う。黒は最後、HP700、パンチなし・既存キック全19種。
- 白はパンチ／キックを別々にランダム発動。通常敵は各色固定4パンチ＋4キック。短射程ほど1技の総威力を高くし、連続技では各打撃へ配分。
- 攻撃同士の相殺は差分ダメージ。100対70は弱い側30、同値は双方0。
- 敵味方共通で7回分の攻撃ゲージ、過熱後3秒の休止。過熱前にも同率で冷却できる。
- 車を蹴って当てると50ダメージ、街の損壊は増える。追加の戦術的メリットを作る必要はない。
- 撃破で100回復、上限500。撃破スロー1.5秒、敗北スロー2秒。相打ちは敗北優先。
- ダメージ粒子、被弾量に比例したHPバーの揺れ、緑の減少分を赤へ変更、粒子吸収後に赤を縮める演出。
- スワイプ移動、パンチ／キック／ジャンプボタン。位置・サイズ・透過率設定。長押しや連打を必須にしない。

### 計画上の初期値と確定要件の違い

設計書で「提案」とした内容は、本計画でも初期設計値であり、本人が個別に確定した要件へ読み替えない。青→緑→黄の順番、混合技AcrobaticComboをパンチ抽選から除く案、配点、車の耐久値、相殺の接触条件、1技＝熱量1、技終了後に冷却3秒、攻撃中は冷却しない、冷却をポーズ除外実時間とする案などを決定台帳に残す。実装依頼時にこの計画を基準とすることを確認し、未確定部分があれば、その部分だけ保留する。数値調整は範囲を記録し、ゲーム内容・権限の拡張と混同しない。

## 3. 完成品のシステム連携図

以下の図と、添付の図解PDFを対応させる。四角内のA〜Dは実装責任を示す。矢印はデータの向きであり、HPや勝敗の書込み権限はAだけ。

```text
画面への指操作
    │
    ▼
[D 入力] ── 操作コマンド ──► [A 状態・AI・技開始・時計]
                                 │ 技ID / 攻撃時刻 / 移動要求
[B 検証済みモーション定義] ──────┼────► [C 移動・街・車・接触候補]
  ルート曲線 / 打撃区間 / 判定体   │                     │
                                 │         接触候補 / 時刻 / ID
                                 ▼                     ▼
                       [A 相殺 → 命中 → HP → 勝敗・熱量・採点]
                                 │ 確定イベント / 読取専用状態
              ┌──────────────────┼───────────────────┐
              ▼                  ▼                   ▼
      [B 動きの再生]      [C シーン・横カメラ]   [D HP・熱量・粒子・結果]
              └──────────────┬───┘                   ▲
                             │ 命中点の画面座標 ──────┘
                             ▼
                       ブラウザへの描画
```

表示側のアニメーション終了、粒子吸収終了、HPバーの赤い残像の終了は、戦闘値を変更する条件にしない。Bの検証済み技時間をAが読み、Cは同じ時刻でルート移動・打撃位置を評価する。描画の遅れで攻撃回数や判定が変わらないようにする。

### 1ステップの処理順

1. ポーズ／背景化を判定。入力を正規化し、AIも同じコマンド経路を使う。
2. Aが発動可否、抽選、熱量、現在の技時間を決める。
3. Bの決定的な曲線・技定義を使い、Cが移動と空間接触を評価する。
4. Aが同じ時刻の接触候補をまとめ、相殺を先に解決。使った打撃の身体命中を二重加算しない。
5. HP／車50／損壊台帳／撃破／敗北優先／回復／クリア／採点をAが確定する。
6. 読み取り専用snapshotとイベントをB/C/Dへ渡し、カメラ・動き・表示を更新する。

### 時計の契約

- simulationTime：移動、攻撃、AI、命中、スロー対象。固定刻みで進める。
- activeRealTime：ポーズと背景化を除く実時間。演出の1.5秒／2秒、冷却3秒の初期案に使う。
- presentationTime：表示補間用。HPや採点の正本にはしない。
- 長い停止後に失われた時間を一括で攻撃へ換算しない。復帰時は入力解除・再開確認。

## 5. 並列実装の段階と合流点

| 段階 | A | B | C | D | 合流の条件 |
| --- | --- | --- | --- | --- | --- |
| P0 土台 | 契約・入口・検査設定を作る | 原本／技一覧調査 | 座標・接触・カメラ案確認 | 入力／HUDイベント案確認 | 契約v1、所有範囲、基準SHAとテスト入口が確定 |
| P1 並列単体 | 熱量・相殺・HP・状態の純粋検査 | 素材ロード・曲線・破壊2本 | 街骨格・車・移動・横カメラ | 仮イベントで入力・HP演出・設定 | 各担当の契約検査と単体検査、独立fixtureが成功 |
| P2 最小実戦 | 1敵の実判定へ接続 | 白＋通常敵の実GLB | 同じ街で白＋敵＋車1台 | 実イベントへ接続 | 素材・相殺・過熱・車・HP吸収が一連で成立 |
| P3 完成範囲 | 4体進行・黒・採点 | 全技・色・破壊遷移 | 通り・市民・戦闘間移動 | 全画面・結果・復帰 | 4体クリアと途中敗北を再現し、仕様漏れなし |
| P4 統合検証 | 全体・乱数再現・境界 | 曲線と視覚一致 | 壁際／低fps／遮蔽 | タッチ／縦横／設定 | 統合候補commitで全検査、実画像、性能記録 |
| P5 提出 | 最新mainへ更新して再検証 | 差分・素材証跡確認 | シーン証跡確認 | UI証跡確認 | Draft PR、本人マージ判断、公開は別許可 |

P0は短い直列区間。本人によるP0のマージを実物で確認し、全員が同じ新main SHAを取得してからP1実装を開始する。契約commitがあるだけでは開始しない。待機中は読取調査・fixture設計を進める。ここを省いて4人が別々の型やpackage設定を作らない。P1以降は4担当が並行できる。P2で最小実戦が成立する前に、街の装飾量だけを増やさない。未完了の担当を別担当で重複起動しない。

## 7. 完了判定と証跡

各仕事は「提案」「実装済み」「ローカル検査済み」「CI済み」「統合済み」「公開済み」「実機確認済み」を分ける。PR作成だけでは完了ではない。

実装後に予定する検査入口：format、lint、typecheck、unit、contract、build、integration、browser。具体的なnpm script名とツール版はP0でAが登録し、個別計画の予定コマンドを統一する。現時点では未作成・未実行。

完了証跡には要件ID、base SHA、head SHA、契約版、素材manifest hash、コマンド全文、exit code、正式ログ、画面画像、残る制限を含める。モバイル画面サイズの自動検査と実機Safari確認は別。iPhone17 Proを主対象、11 Pro／iPad Pro2018は低負荷設定を含む補助確認とし、未確認を合格表示しない。
