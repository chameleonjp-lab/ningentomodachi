# 担当D 実装計画：操作・画面・HUD

作成日：2026年10月22日  
基準：`design/2026-10-22-ningentomodachi-design-review-v6.md` の第2〜5・8〜12章  
状態：計画のみ。以下のソース、テスト、コマンド、PRは将来の実装予定であり、作成済み・実行済み・動作確認済みではない。

## 1. 目的と完了範囲

スマートフォンで、左スワイプ移動と右側のパンチ・キック・ジャンプを同時に操作できる画面を作る。タイトル、読込、失敗、設定、ポーズ、結果を用意し、白と現在の敵のHP・熱量・過熱状態を正しく表示する。ダメージの意味が見て分かり、表示演出が勝敗・回復・時計に干渉しないことを最優先とする。

担当Dは画面表示と入力意図の受け渡しに限定する。ゲームのHP、熱量、攻撃可否、死亡、撃破数、得点、ステージ進行、時計の正本は担当Aが所有する。Dが複製した戦闘計算で「おそらくこの値」と表示する方式は禁止する。

設計書の「確定」と「提案」は区別する。初期配置、透過率の下限、入力の遊び幅、演出時間配分、粒子上限などは調整用の初期案であり、本人の確定指定に書き換えない。ジャンプ中の攻撃可否、入力予約、時計の扱い、熱ロック開始時点などのゲーム規則はAの契約に従う。

### Dの成果物

- 独立した入力アダプターと、停止時に入力を確実に解放する処理。
- 上記の画面群、両者のHP・熱ゲージ、設定の検証・端末内保存・復旧。
- Coreの確定済みダメージ／回復イベントに従うHUD演出と粒子の吸収表示。
- D所有範囲の単体テスト、モック契約テスト、ブラウザ検査、実機検査手順と未実施一覧。
- 統合担当へ渡す公開関数、依存契約の固定版、変更ファイル一覧、検査証跡、既知の制限。

### 今回も将来のD実装にも含めないもの

戦闘計算、攻撃の抽選・予約規則、敵AI、物理・当たり判定、カメラ制御、3D命中点の算出／投影、街の損壊計算、採点式、モデル・モーション制作、ランキング送信、アカウント、課金、共有基盤の独自変更。DのHPバー揺れを全画面やカメラの揺れへ拡大しない。

## 2. 所有パスと共同作業の境界

以下は将来作るパス案。Phase 0で実際のリポジトリ構成と合わせて固定し、以後の担当間の境界とする。

| 所有者 | パス・対象 | Dの扱い |
| --- | --- | --- |
| D | `src/input/**` | 入力意図、pointer管理、解放、移動軸の参照保持 |
| D | `src/ui/**` | 画面、HUD、設定、UI CSS、2D吸収粒子 |
| D | `tests/input/**` | 入力単体・契約検査 |
| D | `tests/ui/**` | HUD・画面・設定の単体検査、D範囲のブラウザ検査、fixture |
| A | 共有契約、Core、状態・時計・採点、アプリbootstrap、`package.json`、lockfile、共通設定 | 読み取りのみ。必要な変更は理由と契約テスト案をAへ依頼 |
| B | 素材・アニメーション | readinessとエラー状態をA経由で利用。原本やモーションに触らない |
| C | ワールド、移動の実体、カメラ、衝突、3D火花、命中点の画面投影 | 読み取り契約を利用。カメラ行列や投影計算をDへ持ち込まない |
| A（統合コード所有者） | 全体E2E、統合コード、統合ブランチの実装 | D範囲を超える結線や横断検査はAへ依頼 |
| 親オーケストレーター | PR順序、品質ゲート、担当間調整、本人への確認・報告 | 第5の実装担当ではなく、A〜Dのコード所有境界を維持して調整する |

本書の「統合担当」はコード所有者Aを指す。親オーケストレーターはAの代わりに統合コードや全体E2Eを編集せず、レビュー・PR・品質確認の進行を調整する。

UIのスタイルはルート要素配下へ閉じ込める。全体CSS、共有状態、共通テスト設定の直接変更で他担当へ影響を出さない。UI向け画像・フォントを外部から追加取得する必要がある場合は、権利と追加ファイルの扱いを先に調整する。標準UIだけで始め、追加素材を前提に作業を止めない。

マスター側と共有する契約パス候補は、`src/contracts/{ids,clock,motion,combat,spatial,commands,events,snapshot,ports,index}.ts`。Aが単独所有し、Phase 0で正式名称と内容を固定する。結線先の候補はA所有の `src/app/{createGame,frameLoop,bootstrap}.ts`。`main.ts`、`index.html`、package・lockfile・共通configもAの所有とする。Dの公開入口は `src/ui/index.ts` と `src/input/index.ts` からexportするfactoryにまとめ、Aが注入する契約だけに依存する。Coreイベントの名称やschemaをDで別名・別定義へ変更しない。

### Phase 0の完了判定

1. A・Cと、座標系・単位・イベント順・重複の扱い・時計・停止／復帰・敵切替を合意する。
2. Aが契約版と利用例を固定する。P1開始後に作成するDのfixtureはその型をimportし、共有型のコピーを作らない。
3. AがD用テストの実行方法、アプリへの登録方法を示す。Dがbootstrapやpackage設定を直接編集せず組み込める。
4. Dの未決事項を「表示調整」と「ゲーム規則」に分ける。後者はAへ差し戻す。
5. Aの契約を変更する場合は、先に影響担当とテストを洗い出し、版を更新する。暗黙の型回避や仮のHP算出で先行しない。

### P1実装の開始ゲート

担当DのP1実装は、P0のPRを本人がマージしたことと、その結果の新しいmain SHAをA〜D全員の共通起点として確認した後だけ開始する。Draft PRの作成、レビュー承認、未マージの契約固定コミットだけでは開始条件を満たさない。親オーケストレーターがマージ結果と共通main SHAを確認し、Aの契約版との一致を記録する。マージ前のDは調査、契約レビュー、fixture・検査ケースの設計だけを行い、ソース、テスト、fixtureの実装を先行しない。

## 4. 入力仕様

### 4.1 スワイプと3ボタン

- 左の操作領域のpointerを移動専用として追跡する。開始位置からの方向と距離を正規化し、離すとゼロ入力を送る。小入力の歩き、大入力の走りへの変換は合意済みのA／C契約に従う。
- 右にパンチ・キック・ジャンプを配置する。1回の押下から1要求だけを送り、長押しや連打を必須にしない。pointerとclickの重複やキーリピートで二重発動を作らない。
- 移動指と各ボタンの指を別々に保持する。同じpointerが複数の操作を奪い合わない。複数の要求が同時に来たときの優先順位・拒否・予約はAが決める。
- 発動済みの技を指の解放で取り消したり、Dが技を再抽選したりしない。過熱中のボタン状態はAの攻撃許可と理由を表示し、D独自に熱量を引かない。
- 移動・ジャンプは、過熱という理由だけで停止しない。敗北など他の停止理由はAの許可状態に従う。
- 横視点への移行時も、置いたままの指の基準軸はその指を離すまで保持する。Dは開始時のCの基準参照を入力へ添え、Cが世界移動へ変換する。Dでカメラ角度を推測しない。

### 4.2 残留入力の防止

pointerup、pointercancel、lostpointercapture、画面回転、viewport変更による再配置、window blur、背景化、設定開始、ポーズ開始、読込中断、敗北、画面破棄で該当pointerを解放する。全解放は冪等にし、重複しても新たな攻撃を出さない。

停止へ入る要求を出した段階で入力を解放し、Aから復帰を確認するまで新規ゲーム入力を受け付けない。背景から戻った指・押下状態は復元せず、新しい操作を必要とする。設定を閉じた時点で背景化や別の停止理由が残る場合は、勝手にゲームを再開しない。復帰手順とpause reasonの優先順位はAに委ねる。

ゲーム操作領域内のスクロール・文字選択・ブラウザの二重イベントを抑える。OS端ジェスチャー、通知センター、Safari固有の操作を完全に禁止できるとは約束しない。失われた入力を安全に解放できることを受け入れ条件とする。

## 5. 画面と設定

### 5.1 画面遷移

| 画面・状態 | Dの表示／要求 | Aが決定すること |
| --- | --- | --- |
| タイトル | タイトル、開始、設定 | 開始可能か、読込へ進むか |
| 読込 | 合意済み進捗、待機表示 | readiness、完了、失敗。根拠のない進捗率を出さない |
| 読込失敗・中断 | 分かる範囲の原因、再試行、タイトルへの導線 | 再読込と復旧。欠けたモデルでプレイさせない |
| プレイ | 両者HUD、入力、設定／ポーズ入口 | 戦闘進行・状態値 |
| 設定 | 配置プレビュー、サイズ、透過率、初期配置へ戻す、閉じる | プレイの停止と復帰可否 |
| ポーズ・背景復帰 | 停止の説明、復帰可能時の導線 | すべての停止理由を確認した復帰 |
| 敗北／最終撃破演出 | 期限内のHP演出、操作停止、暗転 | 勝敗・結果を即時確定し、所定時間で結果へ移行 |
| 結果 | Aが確定した各項目、再挑戦／タイトル導線 | 新しいセッションの生成 |

### 5.2 配置・サイズ・透過率

- タップ領域は各44 CSS px以上。画面のセーフエリアと利用可能なviewportに収まり、ボタン同士・必須導線と重ならず、完全透明にならない値だけ保存する。
- 保存はviewportに対する正規化座標を基本案とする。縦横変更では現在の安全領域に再計算してclampする。狭い画面で制約を満たせない設定は、安全な初期配置へ戻し理由を表示する。
- 見た目のサイズとタップ領域の関係を明示する。小さく見せる調整があっても、44 CSS px未満の操作領域にしない。
- 設定中はゲームを止め、ドラッグ操作をプレイ入力へ流さない。プレビューが完了するまで戦闘操作は再開しない。
- 設定のスキーマ版、数値の有限性、範囲、欠落、破損を検査する。未知の版や破損データで起動不能にせず、安全な値で開始する。
- 端末内保存が拒否・容量超過・利用不可でも、現在のプレイには変更を適用できる。保存できたと誤表示せず、端末内保存に失敗した旨だけ短く知らせる。
- 初期配置へ戻す機能を用意する。何が戻るかを明示し、関係のない記録・データを削除しない。
- 設定は外部送信しない。UIに新たなアクセス解析を入れない。

## 6. HUDとダメージ粒子

### 6.1 HPと熱量の正本

白と現在の敵にHPバー、数値、熱ゲージ、攻撃不可状態、冷却残り時間を表示する。HPの分母はAの最大HPであり、黒だけ700という値をUI中へ散在させない。敵交代で表示対象IDを更新し、白の熱を初期化しない。

熱ゲージの表示は熱量／上限とし、HPと意味を混同しない。熱量が0へ下がっていてもロックが残るなら攻撃可に見せない。熱量6.5での発動など、Coreが許可する入力をDが独自の閾値で拒否しない。スロー中・ポーズ中・背景化中の残り時間はAの時計を読む。DのsetTimeout等で3秒を独自に消化しない。

### 6.2 ダメージの表示順

1. Aの確定ダメージイベントを受け、数値HPと緑の現在HPを直ちに最新snapshotへ合わせる。論理HPを表示完了まで遅らせない。
2. Cの投影した実命中点を始点として命中粒子を表示し、被弾した機体のHPバーだけを実損失量に応じて揺らす。
3. 失った区間を緑から赤の残像へ置き換える。赤の長さは実際に失ったHP／最大HP。緑の現在HP＋赤の過去HPで意味を示し、赤を生存HPとして扱わない。
4. 画面上の粒子を、同じ対象機体IDのHPバー内の吸収点へ飛ばす。命中点はC、HPバーのDOM領域・吸収点はDが所有する。
5. 吸収後に赤い残像を縮めて消す。粒子の到着や演出終了を回復イベントへ変換しない。

命中の火花など3D低レベルエフェクトはCが担当する。Dはその代替として偽のワールド命中を生成しない。Cの投影位置とDの画面エフェクトを対応づけ、重複する強い発光を避ける。

投影不能・画面外のときの扱いはPhase 0で決める。少なくともHP数値と赤区間の正確な表示は続け、画面中央などを架空の命中点にしない。画面外の代理始点を採用するならCが明示的な状態付きで返す。実際の命中点からの演出を検証する合格ケースは、投影可能な実命中で行う。DOMレイアウトと投影のviewport版が違うフレームでは古い座標を使わず、更新または省略を選ぶ。

### 6.3 相殺・連続命中・回復・終了

- 相殺100対70は、Aが確定した実損失30の側だけを30相当で表示する。70対70は両者ともHP減少・赤区間・吸収による減少・HPバー揺れを出さない。相殺の火花そのものはCの別表現として扱える。
- 致死攻撃の表示量は残HPまで。例えば残HP20へ名目100でも、赤くするのは20分。負のHPやバー外への飛び出しを作らない。
- 同じイベントIDを再受信しても二重に演出しない。履歴はセッション単位で管理し、新しい試合へ漏らさない。
- 同じ対象の短時間の複数命中は、順序付きの小さいキューで処理するか表示だけ集約する。どちらも実損失の区間を一度だけ数え、最後のHPがCoreと一致することをテストする。
- 対象が違うイベントを合算しない。敵交代時に旧敵の遅れた粒子を新敵のバーへ吸わせない。戦闘ID・機体IDを照合して旧演出を終了する。
- 回復が来たら、その対象の古いダメージ残像を整理し、回復後snapshotへ表示を合わせる。遅れて終わる赤区間が回復済みの緑を削らない。表示の整合を保つための整理であり、Aのイベントを書き換えない。
- 同時致死ではAの敗北確定を受け、回復を表示して復活したように見せない。UIは死亡、勝利、回復の可否を判断しない。
- 敗北時はAの残り演出時間内で吸収・赤区間の消失を終える。通常のキュー待ちを短縮／集約し、2秒スロー後の暗転・結果を延長しない。表示fps低下や復帰で期限を越えた場合は期限に合わせて収束させる。
- 最終撃破も結果確定を待たせず、最後の演出だけ行う。敵撃破1.5秒、敗北2秒の実時間はAが管理する。

### 6.4 負荷と見やすさ

粒子を再利用し、同時数、対象ごとの吸収軌道数、履歴容量を上限付きにする。超過分は表示集約で吸収し、CoreイベントやHP更新を捨てない。バーの揺れ幅も上限付きにし、HPバーや数値を読めなくしない。低負荷設定でも「緑→赤→吸収→赤縮小」と正確な最終HPを維持する。全画面の激しい振動・連続点滅で派手さを補わない。

## 7. 実装タスクと進行ゲート

すべて将来実行するタスク。D0〜D7の実装作業は第3節のP1開始ゲートを満たした後に行う。各タスクは、最初に失敗を示す検査を用意し、最小実装、該当検査、型検査の順で進める。ファイル名はPhase 0で整合させる。

### D0：契約とfixtureの固定

- 前提：Aの共有契約初版、Cの投影・移動基準案、テスト基盤。
